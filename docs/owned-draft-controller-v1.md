# Owned draft controller v1 — implementation in review

This controller connects authenticated release files to a fixed native GitHub backend, with separate approvals for draft staging and publication. Ticket #10 remains incomplete. **Native remote writes stay blocked until every required gate is Enforced and a separate publication approval is supplied.** The two current-attempt gates are now observable, but only through the pinned controller's attempt-bound deployment (see below); a settings-only inspect still reports them `Unsupported`, and a positive repository setting or a syntactically valid approval cannot override a gate.

The Rust API accepts only private-constructor `AuthenticatedReleaseFiles`, `VerifiedAppleRelease` and `TrustedReleaseContext` proofs. It snapshots every verified file, including the detached inventory and its bundle, into an owner-only directory; the approved plan binds exact source/config/lock/runtime/run/attempt/context/policy and every asset hash/size. Rehearsals, historical-byte comparisons and producer JSON cannot construct this release plan. Native Apple verification is required before freezing a selected Apple executable; Linux does not silently skip that requirement.

Publication policy is a new v1 contract, separate from the frozen trust schemas. Its independently approved digest binds stable repository/owner IDs, protected default branch, immutable controller workflow, actor/publisher/reviewer IDs, environment identity, freshness/expiry and a separate release-attestation root. GitHub's release-signing root is not inferred from artifact-attestation policy or downloaded files. All observations retain unavailable states: 401 denied, ambiguous 403 and 404 unknown, 410 unsupported, other errors explicit. Reflected error messages grant no authority.

Native GETs bind the exact stable source tag, including bounded annotated-tag peeling; protected default branch and source ancestry; push event; source repository; currently active run/attempt; original and rerun actors and their permissions; immutable referenced controller workflow; and an active exact/all-tag ruleset without bypass actors protecting update and deletion. Unsupported tag-rule shapes are unproven. Settings snapshots and source observations are repeated to detect races. The backend does not claim that these reads establish an atomic compare-and-swap or exclusive authority.

The two current-attempt gates are decided in `source_gates`, where the frozen release carries `run.id`/`run.attempt` and `source.commit`. The trusted pinned controller workflow (`environment: release-publish`) creates one deployment bound to its exact run/attempt **before any publication write**, with payload `{"armorer_run_id", "armorer_run_attempt", "armorer_source_commit"}`. The adapter verifies it through fixed GET routes only — `deployments?environment=<env>`, each candidate's `deployments/{id}/statuses`, and `actions/runs/{id}/approvals` — and records a `ByteIdentity` for every observation. `capability_snapshot` stays settings-only with no run identity, so both gates remain `Unsupported` there; settings alone cannot bind an approval to an attempt.

`current-attempt-environment-enforcement` is Enforced only when exactly one deployment binds this attempt (environment match, `sha == source.commit`, payload run/attempt/source-commit match, creator `github-actions[bot]`), that deployment is active (latest status non-terminal), and `actions/runs/{id}/approvals` shows an approved entry for the policy's `environment_id` by an allowed approver who is neither the actor nor the triggering actor (`prevent_self_review`). `runner-wide-serialization` is Enforced only when exactly one active (non-terminal) deployment exists for the environment and it is the one bound to this run/attempt; the workflow's `armorer-release-controller` concurrency group (`cancel-in-progress: false`) is the real runtime enforcement, and the single active deployment is its API-observable proxy. A second active deployment, a missing/foreign/stale deployment, a run/attempt/commit mismatch or a self-approval yields `Unknown`. The listing is bounded: more than 100 deployments fails closed to `Unknown`. Unavailable reads keep the established mapping (401 denied, ambiguous 403/404 unknown, 410 unsupported, other errors explicit) and never upgrade a gate. Both observations are repeated and compared, so the decision is deterministic.

Residual trust, documented rather than hidden: the workflow must be the immutable pinned controller; a write-access actor inside the existing protected-workflow trust boundary could forge a deployment. This is not an atomic compare-and-swap. The approvals API is run-scoped, so the attempt binding comes from the workflow-written deployment payload, not from the approval record itself. Writes still require every gate Enforced plus the separate publication approval.

The protected state directory must already exist with mode `0700`, outside consuming/build workspaces and accessible only to the trusted controller. A repository-wide kernel lock serializes local tags and is explicitly released when its controller drops, including when a concurrent spawn retains a duplicate file descriptor. Independent Actions runners are serialized by the controller's `armorer-release-controller` concurrency group (`cancel-in-progress: false`), observed through the single active deployment. The journal is private state, not a transferable provider permit; never restore it from an untrusted workspace or unsigned artifact. The reusable controller workflow exists in armorer-workflows (`rust-release-controller-v1.yml`) but stays inert until the owner supplies the digest-pinned approvals and a built armorer binary; no production caller wires it with credentials yet.

The controller records intent and fsyncs the journal before each create, upload or publish. An ambiguous create or upload remains in its intent phase and cannot automatically retry or adopt a matching remote object. A confirmed draft retry requires the same plan and exact release/asset IDs. It refuses foreign releases, extra/missing/replaced assets, wrong uploader/digest, altered ownership marker and any published-to-draft transition. It has no asset deletion/replacement, tag creation/movement or moving-tag API.

After upload, it re-downloads every asset by exact ID, hashes actual served bytes and brackets the downloads with identical release snapshots. The receipt includes the approved plan, release ID, exact asset IDs and byte identities. A separate publication approval must bind that receipt and ID, expire within a day and name an approved reviewer distinct from both the original run actor and the rerun initiator. Missing or zero actor identities block publication approval. The controller re-downloads, rechecks mutable prerequisites and reads the exact draft again immediately before the one publication write. A later remote writer can still race these reads; native publication still requires every gate Enforced plus the separate approval, and this boundary is not an atomic compare-and-swap.

After publication it requires an immutable release, the same tag/source/asset IDs, actual served bytes, genuine `gh release verify` and per-file `gh release verify-asset` results against the separately approved root. It checks the exact signed v0.2 statement, GitHub release certificate SAN, verified timestamp, repository/owner/release IDs, purl, tag object and complete asset subject set. A successful exit alone is insufficient. v0.1 release predicates receive no automatic compatibility fallback. Verification failure retains incomplete state and requires incident review; it never repairs published bytes. An ambiguous publish is recovered through GET-only verification and never a repeated publication write.

The CLI is `armorer publication <common-input-flags> plan|inspect|stage|publish|recover-published`. Common flags are `--directory`, `--trusted-inputs`, `--expect-context-sha256`, `--context-kind`, `--gh`, `--trusted-root`, `--cyclonedx`, `--publication-policy`, `--expect-publication-policy-sha256`, and `--release-attestation-root`. `plan` authenticates inert release files before creating reviewable canonical intent and opens no credential-bearing client. `stage`/`publish` additionally require an independently approved `--approval` file, `--expect-approval-sha256` and `--state-directory`; unmet required gates block them. `inspect` and `recover-published` use an existing `--owner-home` configuration (default current owner HOME) and reject every remote write. Check/plan never execute consuming repository build scripts or modify consuming files.

No credential value is accepted as a flag or returned. The eventual protected job client uses its existing `GH_TOKEN`/`GITHUB_TOKEN` only after authenticating policy/native bytes. The fixed native process clears the environment, closes stdin, verifies executable/root snapshots before every call and bounds stdout/stderr/time. It uses fixed GitHub API/upload authorities; it never consumes provider-returned URLs or caller shell/provenance inputs.

Validation combines private state-machine doubles (ownership/retries/ambiguity/races/approval/post-publication failures) with authentic native public release-attestation fixtures. The public CLI fixture is not an Armorer release and uses public live root routing in its qualification test; production requires the independently approved release root. Local/hosted tests do not establish protected-job acceptance, an own signed complete inventory, live owned-draft transitions, post-publication operational acceptance or Apple parity. Those gates and human acceptance remain required. No release, tag or settings mutation is authorized by this document.

A separate ignored native test executes the new backend's fixed repository/settings GETs on the real public Armorer repository with existing operator or `contents: read` workflow authentication. It retains actual unavailable states and proves that required attempt/serialization gates prevent readiness. Its owner client rejects create/upload/publish methods before process startup, and offered native/root substitutions are rejected. The test's private synthetic policy selects GET routes only; its root snapshot is not production release-root approval. The test never sends a provider write or changes settings, tags, drafts or assets.
