# ADR 0009: explicit policy and versioned multi-file bootstrap

Status: implemented proposal for #4 review, 2026-10-02. Human acceptance and hosted validation are separate gates; no release claim.

The v1 plan and apply engine authorize only a toolchain mutation. Reinterpreting
those approved plans as permission to write callers, pins or policy would violate
the frozen interface and invalidate existing recovery journals.

The implementation introduces an explicitly selected provisioning plan version 2, separate from v1
plan output. Bind exact config, Cargo discovery, policy bytes, compiled catalog,
ownership state and preimages; preview all generated bytes/diffs and conflicts.
Targets are a fixed toolchain, v1-compatible Armorer lock, explicit project CI
policy and two reviewed unprivileged callers. No arbitrary target, shell, hook,
URL, signer/predicate or template is supplied by consuming input.

Project dependency policy is an explicit owner decision, with every v1 runtime
section required and unknown fields rejected. Do not derive or install a default
license allowlist, waiver or source permission. Validate expiry against current
UTC and retain bounded exact policy bytes in the approved plan.

Use the same persistent kernel apply-lock inode as v1 and a separately versioned
journal/state. Acquire the lock, rederive exact intent/preimages, validate every
operation before writes, stage atomically, preserve modes on updates and retain a
durable commit marker. Roll back matching managed bytes; refuse intervening edits.
Creating required parent directories may leave empty directories after failure;
never delete unknown directories. Tests must inject failures/crashes at every
managed-file and commit-marker boundary, including a retry and exact recovery.

Unowned identical files remain unowned; different bytes conflict. Importing v1
ownership or bespoke workflows is an explicit reviewed migration (#5), never a
force flag. Legacy unfinished journals block all mutation until recovered. Once
v2 ownership is active, updated v1 apply must refuse cross-version writes rather
than modifying independently owned files. Earlier approved v1 operations must not
be expanded implicitly; obsolete readers cannot safely reinterpret v2 journals.

Successful provisioning records local configured state only. GitHub capabilities
remain unknown pending authenticated preflight; CI, Apple signing, rehearsals,
publication and provenance need their separate receipts and human gates.

The embedded catalog/source receipt is a prerequisite under review in PR #7;
exact preview delivery is separately under review in PR #6. Their implementation
is not human acceptance or authorization to merge. Keep all public release,
repository-admin, tag and pilot operations outside this bootstrap transaction.
