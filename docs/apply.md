# Reviewed local apply and recovery

This development slice applies only `rust-toolchain.toml`. Custom workflow and
license-policy files stay untouched. Reviewed workflow catalogs, pin upgrades,
GitHub capability checks, credentials, signing and publication are separate gates.
Applying a toolchain does not make the repository fully configured or CI verified.

## Approve exact intent

Generate a plan outside the consuming checkout, inspect its intent, generated
content, findings and preimages, then record its `plan_sha256` independently:

```sh
armorer --repository /path/to/workspace plan > /tmp/armorer-reviewed-plan.json
# Review the JSON and retain its plan_sha256 in your review record.
armorer --repository /path/to/workspace apply \
  --plan /tmp/armorer-reviewed-plan.json \
  --expect-plan-sha256 APPROVED_64_CHARACTER_DIGEST
```

Do not obtain the approval digest from an unreviewed replacement plan at apply
time. The digest hashes compact typed JSON with `plan_sha256` blank. Whitespace
and object ordering are immaterial; unknown fields, missing canonical fields and
duplicate JSON keys are rejected. Schema/runtime compatibility is exact.

Apply regenerates the preview using the trusted read-only discovery path. Exact
config and optional pin-lock bytes, Cargo manifest/lock inventory, Rust target-path
presence, license and legacy-toolchain preimages, ownership state and generated
bytes must match. `.rs` content still is not source provenance. Stale input fails;
generate and review a fresh plan rather than editing the approved JSON.

## Preservation and ownership

Absent generated files can be created. An identical existing toolchain is left
unchanged and unowned. Different unowned content, a legacy `rust-toolchain`, or
edits to an Armorer-owned file produce a conflict. There is no force/adopt flag.
Resolve the migration deliberately and preview again. No workflow or `deny.toml`
is silently adopted, edited or removed.

`.armorer/state.json` records schema/runtime version, the last approved plan and
exact generated bases for files Armorer owns. Keep this state with the repository
when keeping Armorer-managed configuration. A reviewed new plan can refresh an
owned toolchain only while its current bytes match the recorded base. This does
not implement the separate workflow/tool pin upgrade catalog.

Repeating the same committed approved plan validates freshly derived intent,
inputs, receipt ownership and exact generated bytes, then returns `unchanged`
without rewriting targets or state. Receipts distinguish `toolchain_configured`
from `configured`; `configured`, `ci_verified`, `release_rehearsed`, `published`
and `provenance_verified` remain false in this slice.

## Transaction and recovery

Armorer creates a persistent `.armorer/apply.lock` inode and holds a nonblocking
kernel file lock. A concurrent Armorer invocation fails; the kernel releases the
lock on process exit. Do not delete this file to resolve contention: deleting a
locked inode can allow two independent locks. The empty lock file is local runtime
state and can be ignored by version control.

Before changing targets, Armorer syncs a bounded `.armorer/journal.json` containing
the approved plan and exact before/after bytes. Writes stage in their destination
directory, sync file contents, atomically install each file and sync the directory.
Initial supported mutation hosts are Linux and macOS. Files created by Armorer
use private temporary-file permissions; updates preserve existing permissions.
The transaction spans multiple atomic file replacements, not one filesystem-wide
atomic operation. A durable commit marker distinguishes committed from interrupted
work. Recovery restores bytes; it does not promise original timestamps or inode
identity. Temporary staging files can remain after abrupt termination; inspect
and remove only confirmed abandoned staging files after recovery.

Ordinary write failures roll back completed writes only when current contents
match transaction preimages or generated bytes. If another writer intervenes,
Armorer preserves the journal and every conflicting file. Subsequent apply is
blocked until explicit recovery:

```sh
armorer --repository /path/to/workspace recover \
  --expect-plan-sha256 ORIGINAL_APPROVED_DIGEST
```

Recovery needs the journal's original independently retained approval digest. An
uncommitted journal rolls back; a committed journal finalizes only when all exact
after bytes match. Wrong approvals, malformed journals, redirected paths and
intervening edits fail without discarding evidence. Preserve a backup of the
journal and conflicting files, inspect the before/after evidence locally, restore
the affected paths deliberately to their recorded before or after bytes, then
rerun recovery. Never delete the journal to bypass an unresolved conflict.

Plans, state and journals are each bounded to 1 MiB. State and journals contain
configuration bytes, not credential values. Armorer never requests secrets.
Check/plan stay read-only and report unfinished transactions. The OS, installed
rustup tools and a stable local filesystem are trusted; file locks coordinate
Armorer processes and do not sandbox hostile writers or a hostile filesystem.

Primary sources: [Rust kernel file locks](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock),
[same-filesystem temporary persistence](https://docs.rs/tempfile/3.27.0/tempfile/struct.NamedTempFile.html#method.persist).
